A keyword cluster fails in two opposite ways. Too few pages and you leave demand on the table. Too many overlapping pages and you compete with yourself.

**Keyword cannibalization** is that second failure: two or more live URLs fighting for the same primary query, the same one-sentence answer, or the same SERP slot - so Google splits signals and ChatGPT has no clear page to cite.

This post is the check I run before a new cluster page ships, and again when Search Console looks weird. It sits next to [keyword clusters at scale](/blog/keyword-clusters-ai-scale/) (the map) and [Google vs ChatGPT content systems](/blog/google-vs-chatgpt-content-system/) (the draft loop).

## What keyword cannibalization looks like in a cluster

Classic SEO cannibalization is "two posts targeting the same money keyword." Inside a cluster it is subtler. Support pages are *supposed* to sit near each other. Near is fine. Same job is not.

| Healthy overlap | Cannibalization |
| --- | --- |
| Pillar covers the topic; support page covers one sub-intent | Two pages both try to own the same primary query |
| Shared vocabulary, different one-sentence answers | Near-duplicate intros and interchangeable outlines |
| Sibling links because a reader would click | Soft duplicates hoping "more URLs = more rankings" |
| One clear winner per query in Search Console | Two URLs swapping positions for the same query week to week |

**Rule of thumb:** if you can swap the H1s and neither page feels wrong, you do not have two pages. You have one page wearing two URLs.

That also wrecks [GEO / ChatGPT citations](/blog/rank-in-chatgpt-answers-geo/). Answer engines keep a handful of sources per reply. Two mushy siblings teach the model nothing unique. One sharp page does.

## The pre-publish cannibalization check

I run this before the MDX file leaves draft. AI drafts are especially good at reinventing a sibling you already shipped - so the gate matters more when the cluster is growing fast.

### 1. Write the one-sentence answer first

For the candidate page, finish this line:

> If a stranger only reads one sentence, they learn: _____.

Then open every live sibling in the cluster and compare. Same sentence? Merge. Adjacent sentence with a different job? Keep.

Example from this site's own topic:

- Pillar-ish: "A keyword cluster maps one money keyword into useful supporting pages without thin spam."
- This page: "Cannibalization checks catch cluster pages that steal each other's primary query before they dilute rankings and citations."

Related. Not interchangeable.

### 2. Lock one primary query per URL

Each page gets:

- **Primary query** (the SERP fight you are willing to enter)
- **Secondary queries** (related, allowed to co-rank softly)
- **Out of scope** (queries you will *not* chase on this URL)

If two drafts share a primary, one of them is lying. Demote one to secondary, change the angle, or kill the draft.

I keep this in the five-line brief from the dual-channel system: intent, primary query, one-sentence answer, fingerprint, links. No brief → no publish.

### 3. Diff the fingerprints

A fingerprint is the lived detail only that page carries - a table you built, a failed experiment, a named process, a constraint you actually hit.

Ask:

1. Does this page teach something a sibling does not already teach?
2. Would a summarizer invent this page from neighboring posts alone?
3. If I deleted this URL, would a reader lose a specific answer?

No / yes / no → cannibalization risk. Fix the angle or do not ship.

### 4. Title and H1 collision test

Put candidate title next to live titles. Red flags:

- Same head noun + soft adjective swap ("complete guide" vs "ultimate guide")
- Same comparison pair with different filler words
- Support page title that restates the pillar without a narrower job

Titles can share a topic word. They cannot share a job description.

### 5. Internal link role test

Before publish, decide:

- Does the pillar link to this page for a *specific* reason?
- Which 1-3 siblings should link here, and with what anchor?
- Does this page link back without pretending to be the pillar?

If you cannot name the link role, the page is probably a duplicate wearing a new slug.

## After publish: Search Console cannibalization signals

Pre-publish checks miss some fights. Weekly-ish Search Console review catches the rest.

I look for:

1. **Query → multi-URL** - one query shows impressions/clicks across two of your cluster URLs
2. **Position thrash** - two URLs swap average position for the same query
3. **Wrong winner** - a thin support page outranks the page you intended for that intent
4. **Impression split with flat clicks** - coverage without a clear click destination
5. **Sudden sibling drop** after a new publish - classic self-competition spike

None of these alone prove cannibalization. Together with a title/intent overlap, they usually do.

Honest limit: Search Console will not tell you about ChatGPT citation fights. For answer engines I still spot-check prompts. If two of my URLs could answer the same question and neither gets named, I treat that like cannibalization of *attention* - merge the mush, sharpen the survivor.

## Fix patterns: merge, narrow, redirect, or kill

When two pages collide, I pick one move. I do not "add more synonyms" and hope.

| Move | When | What I do |
| --- | --- | --- |
| **Narrow** | Both pages have a real fingerprint | Rewrite the weaker page to a stricter sub-intent; change primary query, H1, and opening answer |
| **Merge** | Fingerprints belong together | Fold unique bits into the stronger URL; expand sections; update internal links |
| **Redirect** | One URL has no remaining job | 301 the loser to the winner; fix anchors that pointed at the dead page |
| **Kill** | No traffic, no fingerprint, no link equity worth keeping | Delete or unpublish; remove from cluster map |
| **Demote** | Support page accidentally acts like a pillar | Strip broad claims; point hard to the real pillar; own only the sub-job |

Default bias: **one canonical URL per primary query**. Clusters win on coverage of *different* jobs, not on synonym density.

## A 10-minute cluster cannibalization audit

When the map feels bloated, I run this pass on the whole cluster:

1. Export live slugs + primary queries + one-sentence answers into a table
2. Highlight any shared primary query (instant fail)
3. Highlight near-duplicate one-sentence answers (merge candidates)
4. Check Search Console for multi-URL queries in the topic
5. For each collision: narrow / merge / redirect / kill
6. Update the cluster map so AI scaffolding cannot resurrect the dead intent
7. Re-check internal links so orphaned anchors do not point at ghosts

Step 6 matters. If the map still lists a killed intent, the next AI outline will draft it again. Cannibalization returns as a process bug, not a one-off accident.

## FAQ: keyword cannibalization in clusters

### What is keyword cannibalization?

Keyword cannibalization happens when multiple pages on your site target the same primary search intent hard enough that they compete for the same rankings - splitting clicks, links, and clarity instead of reinforcing one winner.

### Do keyword clusters cause cannibalization?

They can, if you publish overlapping intents. A good cluster *prevents* cannibalization by assigning one job per URL. A bad cluster is just synonym spam with nicer filenames.

### How do I check for cannibalization in Google Search Console?

Look up important queries and see whether multiple URLs from your site appear for the same query, especially with thrashing positions. Pair that with a manual intent diff of titles and opening answers - Search Console shows symptoms; the brief shows the disease.

### Should every cluster page target a different keyword?

Every page should own a different **primary** query and a different one-sentence answer. Secondary keyword overlap is normal. Primary overlap is the problem.

### Does cannibalization hurt ChatGPT citations?

Yes, indirectly. If two pages say almost the same thing, neither looks like the primary source. One specific, quotable page is easier for an answer engine to trust than two soft duplicates.

## Ship coverage, not clones

Cannibalization checks are not anti-growth. They are how a [keyword cluster](/blog/keyword-clusters-ai-scale/) stays useful when AI makes drafting cheap.

One intent. One primary query. One fingerprint. One URL.

Run the check before publish. Audit Search Console after. Merge without ego. That is how clusters compound for Google *and* stay citable when ChatGPT only keeps a few sources in the room.
